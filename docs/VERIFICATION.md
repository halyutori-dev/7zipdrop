# 検証記録 — 何をどこまで確認したか

「テストが緑」だけでは動く証拠になりません。検証レベルを区別して記録します。

## A. 実測で確定した 7zz の契約

`docs/VERIFIED-7ZIP-CONTRACT.md` に 38 項目（うち #23〜#38 は v1.1 の展開機能で追加）。
すべて同梱バイナリを実際に動かした結果か、配布物同梱の `MANUAL/` の記述です。推測は含めていません。

この過程で見つかった、**推測で書いていたら気づかなかった**もの:

1. `7zz a` は既存書庫を上書きせず**黙って追記**して exit 0 で終わる → 自動リネームが必須と判明
2. zip のパスワード既定は **ZipCrypto**（実質破られる） → `-mem=AES256` の強制が必要と判明
3. 絶対パスで渡すと basename に潰れ、同名衝突は**致命的エラー** → cwd + 相対名方式に変更
4. `-spd` はワイルドカード除外 (`-xr!._*`) も無効化する → A/B 実測で発見、リテラル除外のみに変更
5. 進捗は CR ではなく **backspace(0x08)** 区切り → 実バイト列を golden fixture 化
6. `-sse` 無しだと読めないファイルを黙って除いた書庫が exit 1 で作られる → 既定を fail-closed に
7. `t` / `x` / `e` / `l` は**パスワードを標準入力から読まない**（pipe / pty 両方で確認）→ 暗号化書庫の検証・展開方針を変更
8. Zip Slip と絶対パス entry は 7-Zip 26.02 側で無害化されるが、**exit 0 のまま黙って名前が変わる** → 独立に検査して拒否する設計に
9. 相対ターゲットの脱出 symlink も 7zz 側で拒否される → こちらの事後検査は E2E で発火させられないと判明し、**偽ランナーで直接テストする**方針に変更
10. `l` はパスワード必須の書庫で "Enter password:" を出して待つ → stdin を閉じているため 255 で終わる（ハングしない前提として重要）。ログ文言に "encrypted" は現れないので、判定は実文言にピン留め
11. `-o` に空白を入れると exit 7 の Command Line Error（最初に自分がこれを踏んだ）
12. 同梱ビルドは **`lz4` 非対応** → 自動判別の拡張子リストから除外

### 展開側のテスト

- **敵対的な書庫を fixture 化**: Zip Slip (`slip-rel.zip`)、絶対パス entry (`slip-abs.zip`)、
  symlink 脱出 (`slip-link.zip`)、脱出しない `..` (`inner-dotdot.zip`) を自作して
  `Tests/CompressorCoreTests/Fixtures/` に置き、**既定で拒否され何も配送されない**ことを確認。
  許可設定を on にしたときだけ展開され、書き換えられたパス件数が結果に出ることも確認。
- **展開の E2E**: 圧縮→展開の往復でバイト一致（日本語ファイル名含む）、単一ルートの
  un-nest、単一ファイルはそのまま配送、複数ルートは書庫名のフォルダに、
  `.tar.gz` の 2 段展開、分割書庫を `.003` から開く、暗号化書庫の展開、
  未入力と誤りの区別、サイズ上限での拒否、展開先固定、2 回展開して 1 個目が不変、
  一時ディレクトリが常に消える、**書庫のバイト列が不変**。
- **申告の無い / 信用できない展開サイズ（契約 #42）**: 178 バイト → 200 MB の bzip2 を 10 MiB 上限で
  止めること、空き容量（注入した値）で止めること、上限内なら全量展開すること、1 回の計測間隔より速く
  終わる 12 MB の bzip2 も終了後の計測で止めること、ISIZE を書き換えた gzip を `.bin` という名前でも
  止めること（形式は 7zz が内容から判定する `Type` で見る）を実 7zz で確認。巨大申告の zip64
  （合計が Int64 を溢れる組 / 2^64 近い単独申告）は listing の段階で拒否され、**落ちない**ことも確認。
  いずれも v1.4 では素通り（bz2 等）またはテストプロセスごと SIGTRAP（オーバーフロー）でした。
- **SIGPIPE（契約 #43）**: stdin を読まずに終わる子（`/usr/bin/true`）へ 1 MiB を書いてもランナーが
  0 を返すことを確認。修正前はテストプロセスが signal 13 で死にました。
- **到達不能な層は直接テスト**: 展開後の symlink 脱出検査は、7-Zip 26.02 自身が
  先に止めてしまうため E2E で発火しません（契約 #38）。そこで検査対象のツリーを手で作って
  検査関数を直接呼び、内側リンクは通す / 相対脱出・絶対脱出は拒否する / 深い階層も見つける /
  **リンクを辿って外へ出ない**ことを確認しています。
- **配送のアトミック性**: `renamex_np(RENAME_EXCL)` は競合時にしか効かないため、
  既存の空ディレクトリ・非空ディレクトリ・同名ファイルを相手に mover を直接テストしています
  （空ディレクトリの拒否が、素の `rename(2)` との差そのものです）。

v1.4 で 14 種類（レイアウト 12 + 説明ツールチップ 2）になりました。ツールチップの 2 件は

### この目視確認で見つかった不具合（3 件・すべて修正済み）

1. **進捗が実行中に届いていなかった**（最も重い不具合）。行は出るが最後まで
   「準備中…」のままで、進捗バーは不定表示のままでした。
   計測すると 7zz は 0.2 秒ごとに進捗を出しており、`job.percent` への適用も 32 回
   行われていたのに、**適用のタイムスタンプが全て終了直前の 2ms に集中**していました。
   原因は読み取り側で、`FileHandle.read(upToCount: 65536)` は
   **要求した長さが溜まるか EOF まで返らない**ため、総出力が数 KB の 7zz では
   EOF まで 1 バイトも届いていませんでした。`read(2)` による逐次読み取りに変更。
   → 「進捗が出ること」しか見ていなかった従来のテストでは検出できなかったので、
   **到着時刻の分布**（100ms バケットが 5 個以上・最初の更新が終了の 0.4 秒以上前）を
   検証するテストを追加し、旧実装で赤くなること（`buckets.count → 1`）を確認しました。
2. **初回起動のウインドウが意図したサイズで開かなかった**（900×650）。コンテンツ側の
   `.frame(idealWidth:idealHeight:)` では Scene の既定サイズは決まらないため、
   `.defaultSize(width: 560, height: 840)` を Window シーンに追加。
3. **下部ステータスバーが最後の行に食い込んでいた**。区切り線と下余白を追加。

### さらに見つかった不具合（2 件・修正済み）

5. **保存先が `~/Downloads` などのときに配送が失敗していた**（実アプリでのみ露見）。
   配送は `link(2)` + `unlink` でアトミックに名前を取っていましたが、macOS は
   **保護対象のユーザフォルダ直下に新しいハードリンクを作らせません**。実測すると
   `~/Downloads` 直下への `link()` は `EPERM`、同フォルダの*サブディレクトリ内*なら成功、
   `renamex_np(..., RENAME_EXCL)` はどちらでも成功（契約 #41）。
   **テストが全て `/tmp` の下で走っており、そこでは `link()` が通るため検出できませんでした。**
   配送を `renamex_np(RENAME_EXCL)` に統一し（ディレクトリ用と同じ仕組み）、
   **保護フォルダ直下での配送テスト**を追加しました（`~/Downloads` に一意名の項目を作って
   すぐ消します）。旧実装ではこのテストが `linkFailed(code: 1, path: ~/Downloads/…)` で赤くなります。
6. **「フォルダを作成して展開」を素直に実装すると `Docs/Docs/` と二重に入れ子になった**。
   モックアップではこの設定がオンなので、実装当初は「常に書庫名のフォルダを作る」としましたが、
   書庫が既にフォルダ 1 つを持つ場合に更に包むのは冗長です。意味を
   **「結果が必ずフォルダ 1 つになることを保証する」**に精密化しました:
   - 中身がフォルダ 1 つ → それを container として使う（二重にしない）
   - 中身がファイル 1 つ、または複数 → 書庫名のフォルダを作る
   - オフ → 中身が 1 つならファイルでもそのまま置く
   ツールチップにこの通り明記しています。

### 想定と実測が食い違った点

- **zip は分割できました**（契約 #39）。「zip だと分割できない」という前提で除外するところでしたが、
  実測すると `名前.zip.001` が生成され、`.001` から展開して内容も一致します。さらに全パートを
  `cat` で結合すると **macOS の `unzip -t` が通る標準 zip** になります（単体の `.001` は開けません）。
  そのため zip タブに分割サイズを残し、結合が必要な旨をツールチップに書きました。

## C-4. 設定ペインの余白と枠線（v1.3）

要望は 2 点 — 「設定画面の項目に対する余白を設けて視認性をあげる」「右ペインに枠線をつけて
ペインの切れ目をわかりやすくする」。**目視ではなく実測**で前後を比較しました。

実アプリを捨てバンドル（Bundle ID を差し替えたコピー = 利用者の設定を読み書きしない）で
起動し、`caffeinate -u` で画面を起こしてから `screencapture -l <CGWindowID>` で
ウインドウ単体を撮影し、PNG の画素から寸法を算出:

| 指標 | v1.2 | v1.3 |
|---|---|---|
| 設定行の高さ（カード内の区切り線の間隔・中央値） | 39pt | **47pt** |
| ペイン左端の明度段差（境界のコントラスト） | 22 | **56** |
| 境界の実体 | 半透明素材のにじみのみ | 1pt の実線（明度 93 / 背景 36〜41） |
| ペイン幅 | 380pt | 408pt |

ライトモードも同じ手順で確認しました（`NSRequiresAquaSystemAppearance` を立てたコピーで起動。
利用者のシステム設定は変更していません）。境界の明度段差は **59.4**（暗い線 192 が白 247〜251 の中に
出る）で、ダークモードの 55.7 と同等です。色は `NSColor.separatorColor` /
`NSColor.windowBackgroundColor` を使っているため、両モードで OS 標準の見え方になります。

### この作業で見つかった不具合（2 件・修正済み）

1. **ペインの枠線は最初から描かれていなかった**。`.overlay(alignment: .leading) { Divider() }`
   と書いてあったが、`Divider()` は囲んでいるスタックの軸から向きを決めるため、overlay の中では
   軸がなく**水平**の線になる。実際にはペインの上下中央に横線が 1 本出ていた（撮影画像で確認）。
   `Rectangle().frame(width:)` に置き換え（`PaneEdge`）。幅だけを指定した Rectangle は
   overlay の高さいっぱいに伸びる。
2. **ペインが「Drop File/Directory」の右半分を覆っていた**。半透明だったため気づきにくかったが、
   境界をはっきりさせる（＝不透明にする）と完全に隠れる。ペインが乗る幅だけ本体側を
   譲るようにした（スライドインの動きは維持）。

### 検証用ハーネス自身の誤りも 2 件（この記録のため）

- ウインドウ ID の検索でアプリ名にプロセス名（`SevenZipCompressorApp`）を使い 0 件になった。
  正しくは `CFBundleName`（`7Zip Drop`）。**0 件を「ウインドウが無い」と読まなかった**のが分かれ目。
- 同じアプリが 64x64 の補助ウインドウも持っており、「最初に見つかった layer 0」を撮ったため
  **128x128 の画像を「撮影成功」として受け取っていた**。最大面積のウインドウを選ぶよう修正。

## C-5. 説明ツールチップ・配置・コントラスト（v1.4）

依頼は 4 点 — ツールチップが出ない / 保存先のパスをボタンの下へ / 共通パスワードをパスワードの下へ /
枠線は OS 設定に準じ、専用部品ではなく汎用部品を使う。

### ツールチップ: `.help()` は**何も設置していなかった**

ホバー操作は自動化できません（Accessibility 未許可のため合成 mouse-moved が破棄される。
`CGWarpMouseCursorPosition` でカーソルは動くが、イベントは配送されない — ツールバーの歯車
ボタン（標準 Button + `.help()`）でも何も出ないことを確認したので、これは**ハーネスの限界**で
あってアプリの判定材料にはなりません）。

そこで観測対象を変え、アプリ自身に自分の NSView ツリーを歩かせました
（`-dumpTooltips 1`、`scripts/check-tooltips.sh`）。**必ず対照を同時に取る**のが要点で、
既知のツールチップを持つ `NSButton` を注入して再カウントし、`control=1` を確認します
（これが無いと「0 件」は「無い」なのか「見えていない」のか区別できません。実際、最初に書いた
オフスクリーンの `NSHostingView` 版は既知の Button でも 0 を返す**検出力ゼロの観測器**でした）。

結果:

| | tooltipViews | control |
|---|---|---|
| v1.3（`.help()` のみ） | **0** | 1 |
| v1.4（システムツールチップを設置） | General **13** / 7z **4** / Zip **3** / ペイン閉 **0** | 1 |

`.help()` は VoiceOver 用に残し、表示は AppKit の `NSView.toolTip`＋`NSTrackingArea` に
渡しています（自前のポップアップは描いていません＝OS の汎用ツールチップ）。当たり判定は
**行全体**（実測 371x46pt）に付けたので、11pt のアイコンを狙う必要はありません。

診断コードは `#if DEBUG` に入れてあります（永続 domain に `dumpTooltips` が書かれた
シェルの出荷版が起動直後に終了して「壊れた」ように見える事故を避けるため。release バイナリに
`TOOLTIP-DUMP` 文字列が 0 件であることを確認済み）。したがって**計測できるのは debug ビルド**で、
出荷する release との同一性は「ツールチップ配線に `#if` が 1 つも無い」ことをテストで
固定して担保しています。

ゲート自身の非ハーメティック性も 1 件修正しました。`appSettingsV2` が永続 domain に
残っていると件数が変わるため（保存先=指定フォルダ でパス行が 1 個増え、パスワード=毎回共通 で
共通パスワード行が 1 個増える）、引数 domain で 3 つの設定キーを潰して既定値から起動させています。
**汚染を実際に注入して確認**しました: 対策なしでは General 13→14 / 7z 4→5 になり、対策後は 13 / 4。

**まだ検証できていないこと**: ツールチップが「設置されている」ことは測れましたが、
**ホバーで実際に表示される瞬間**は自動化できていません（上記の理由）。VoiceOver での
読み上げも未確認です（説明は `.help()` と `.accessibilityHint` の両方で渡しています）。

### 枠線: 汎用部品へ + コントラスト設定

- 専用の `PaneEdge`（`Rectangle`）を廃止し、**`Divider()` を `HStack` に入れて**縦線にしました。
  行間の区切りも `Divider()` そのままにし、上に色を重ねるのを止めました。
- ただし **`NSColor.separatorColor` は「コントラストを上げる」設定に反応しません** — 実測:
  `aqua` / `darkAqua` / `accessibilityHighContrastAqua` / `accessibilityHighContrastDarkAqua`
  の 4 通りすべてで alpha 0.098、色成分も同じ。`windowBackgroundColor` /
  `controlBackgroundColor` も同様。
  そのため `@Environment(\.colorSchemeContrast)` を読み、`.increased` のときはペインの線と
  カードの枠を `labelColor` に強めています。
- 外観別のレンダリングは、`-forceAppearance <NSAppearance 名>` で**実際に適用されたかを
  アプリに出力させてから**撮影しました（`effective=` を確認。最初は NSApp にだけ設定していて
  ウインドウに効かず、次は stdout がブロックバッファされて出力を取り逃していました）。

| 外観 | 適用確認 | ペイン境界の明度段差 | 線/背景 |
|---|---|---|---|
| Aqua（ライト） | effective=Aqua | 58.4 | 192 / 250 |
| DarkAqua（ダーク） | effective=DarkAqua | 55.6 | 95 / 38 |
| AccessibilityHighContrast* | **適用されず**（effective=DarkAqua に落ちる） | — | — |

**macOS は高コントラスト外観をアプリ側から指定させません**（要求しても通常の外観に落ちる）。
実際の「コントラストを上げる」設定を入れた描画は**未確認**です — この分岐はテストと
mutation（削除すればスイートが赤くなる）で固定していますが、見た目の確認は残っています。

## C-6. アプリアイコン（v1.4）

`Resources/AppIcon-1024.png`（提供された原画・フルブリードの 1024x1024・アルファなし）を反映。

macOS のアイコングリッドは**推測せず実測**しました。`Finder.icns` を `iconutil` で展開して
アルファの外形を測ると、本体は canvas の **80.5〜83.6%**、角丸半径は本体の **約 22%**。
Apple が公開しているグリッド（1024 canvas / 824x824 本体 / 半径 185.4px）と一致するので
その値を採用しています。角丸は自前の近似ではなく `CALayer` の
`cornerCurve = .continuous`（OS 自身の squircle）に描かせています。

検証:

| 確認したこと | 方法 | 結果 |
|---|---|---|
| 本体サイズと余白 | 生成 PNG のアルファ外形を測定 | 1024 で 824x824 @ inset 100 / 32 で 26x26 @ inset 3（システムアイコンと同一） |
| 角が実際に抜けているか | 四隅のアルファ値 | 0（中央は 255） |
| 生成が決定的か | 2 回生成して差分 | バイト一致 |
| **OS が実際に描くアイコン** | `NSWorkspace.icon(forFile:)` を PNG 化 | 新しい原画。16〜2048 の 32 representation |
| 監査ゲート | icns の 10 スライス / 最大 1024x1024 / サイズ >500KB | PASS（切り詰め・削除の両方を注入して赤くなることを確認） |

### この作業で見つかった不具合（1 件・修正済み）

**`CALayer.render(in:)` はレイヤの位置を無視します**。`layer.frame` に余白分の origin を
入れていたのに、生成画像の本体は **canvas の角に密着**していました（アルファ外形の測定で発覚。
目視では「余白のないアイコン」に見えるだけなので気づきにくい）。余白はコンテキストの
`translateBy` で与えるよう修正しました。

## D. 検証**できていない**こと

正直に列挙します。ここは引き渡し対象です。

1. **マウスによる実際のドラッグ&ドロップ**: 合成クリック・ドラッグには Accessibility 権限が
   必要で（`AXIsProcessTrusted` は DENIED）、自動化できていません。ドロップ処理は macOS 標準の
   `NSPasteboard.readObjects(forClasses: [NSURL.self], options: [.urlReadingFileURLsOnly: true])`
   を使っており、投入後の経路は C で確認済みですが、**ウインドウへドラッグする操作そのものは未検証**です。
2. **UI の操作**: 同じ理由でクリック操作を伴う確認は未検証です — 歯車ボタンでの開閉アニメーション、
   タブの切り替え操作そのもの、フォルダ選択パネル、**パスワード入力ダイアログの実操作**、
   ツールチップのホバー表示。各タブの表示と各設定の既定状態は C-3 で確認済みで、
   パスワードの各モード（しない / 都度質問 / 毎回共通）の**ロジック**はエンジン側テストで
   確認していますが、ダイアログを実際に操作した確認はできていません。
3. **「毎回共通」でキーチェーンに保存する経路の実操作**: 保存 / 読み出し自体は
   `KeychainPasswordStore` のテストで実キーチェーンに対して確認していますが、
   アプリの UI から設定する操作は未検証です。
4. **暗号化書庫を UI から展開する操作**: パスワード欄への入力を伴う操作は自動化できていません。
   エンジン側の経路（未入力・誤り・正解、ヘッダ暗号化を含む）は E2E テストで確認済みですが、
   「パスワードで再実行」ボタンの実操作は**未検証**です。
5. **通知の実表示**: ad-hoc 署名では通知権限の要求が失敗することがあります。その場合も
   通知が出ないだけで圧縮は正常に動きます。
4. **Intel Mac 上での実行**: 同梱 7zz は universal binary で、アプリ側も arm64 / x86_64 の
   どちらでもビルドできますが、実機確認は Apple Silicon のみです。
5. **巨大な入力での実運用**: テストで扱った最大は約 126 MB です。数十 GB 規模での
   メモリ挙動・所要時間は未計測です。
6. **配布**: ad-hoc 署名のため、他の Mac に配ると Gatekeeper に止められます。配布するには
   Developer ID 署名 + notarization が必要です。
